# Nix: The Purely Functional Software Deployment Model (Nix ecosystem)

Nix's durable idea is not a build language but a _store discipline_: every
component is an immutable value at a path derived from all of its inputs, so
building, deploying, rolling back and garbage-collecting become operations on a
purely functional data structure. The 2006 thesis defines that model and its
build algorithm; the 2010 NixOS article is the largest proof that it scales from
packages to an entire Linux system. Vocabulary in this page is [concepts]'s;
_scheduler_, _rebuilder_, _trace_, _minimality_ and _early cutoff_ are not
redefined here.

**Last reviewed:** November 2, 2026

## Overview

### What it solves

The thesis starts from _correct deployment_: "given identical inputs, the
software should behave the same on an end-user machine as on the developer
machine" (§1.1, p. 3). Its diagnosis is that conventional package managers have
no reliable dependency graph — an undeclared library can be found in `/usr/lib`
and the package still "works" on the developer's machine — and that destructive
upgrades make rollback and side-by-side versions impossible. The proposed fix is
to make the component, not the installation directory, the unit of identity:
store each build result under a path containing a cryptographic hash of every
input, and never modify it.

> "In Nix, the contents of a component depend exclusively on the build inputs.
> The advantage of a purely functional model is that we obtain strong guarantees
> about components, such as non-interference."
>
> — Thesis §2.1, p. 21

NixOS extends the same claim from packages to _all static parts of a system_:
configuration files, startup scripts, the kernel and the system configuration
are built the same way.

> "In this model, the static artifacts of a running system – software packages,
> configuration files, system startup scripts, etc. – are generated by functions
> in a purely functional specification language."
>
> — JFP §1, p. 2

### Design philosophy

Three commitments follow from the "purely functional" analogy and explain most
of the design:

1. **A component is a value.** Building is evaluation; upgrading is computing a
   new value, not mutating an old one. The store behaves like a persistent data
   structure, and garbage collection follows references from roots.
2. **The hash is the identity.** A change anywhere in the transitive inputs —
   source, compiler, flags, build script, dependency — produces a different
   path. Two configurations cannot overwrite each other, and a path is a
   complete statement of provenance for the build that produced it.
3. **Purity is the correctness assumption.** If builders are deterministic and
   see only declared inputs, then the hash identifies the contents forever.
   The model does not make builds pure by itself; it makes impurity _visible_
   and, in the thesis's words, makes an undeclared dependency fail
   deterministically rather than silently succeed.

> "Components never change after they have been built—they are marked as
> read-only in the file system."
>
> — Thesis §2.1, p. 21

## How it works

### The store and the store path

The store is a single directory, normally `/nix/store`. Every entry is a
_store object_ — a file, directory or symlink tree — and its _store path_ has
the shape `storeDir/hashPart-name`. The hash part is a 160-bit, base-32
truncation of a SHA-256 hash; the thesis gives the construction explicitly:

```text
makePath(type, descr, name) =
  nixStore + "/" + printHash32(truncate(20, hashsha256(s))) + "-" + name

s = type + ":sha256:" + descr + ":" + nixStore + ":" + name
```

Both the store location and the symbolic name enter the hash, so two stores in
different directories get different hash parts, and a source cannot impersonate
an output (`type` differs). The truncation to 160 bits is a compatibility
decision: it keeps the hash part 32 characters, preserving file-name limits
that a full 52-character base-32 SHA-256 would exceed (thesis §5.2.2,
pp. 92–95).

Immutability is enforced by permissions: after a successful build the output is
canonicalised — timestamps set to the Unix epoch, modes set to `0444` or `0555`,
setuid/setgid removed — and the path is registered as _valid_ in a transactional
database. A valid path's contents are supposed to be fixed; `nix-store --verify
--check-contents` rechecks the stored SHA-256 (`Invariant 2`, §5.2.3).

### Hash scanning finds retained dependencies

Declared build inputs are not the whole graph. A linker may embed the path of a
library in an executable's `RPATH`, a script may hard-code an interpreter, and
a Java class may name another class. Nix finds these _retained_ dependencies
generically, without knowing file formats, by scanning the output for the hash
parts of every input: the hash part is distinctive enough that a match is
evidence of a reference. The thesis justifies this as the deployment analogue of
a conservative garbage collector (§2.1, pp. 23–24, pointing to §3.4), and the
resulting `references` graph is what makes closure copying and garbage
collection sound.

### Nix expressions become store derivations

Nix expressions are a lazy, purely functional language for describing
components and their composition. They are **not** built directly. A
translation step (`nix-instantiate`) evaluates an expression to a graph of
_store derivations_ — one per build action, with all variability removed — and
writes each `.drv` into the store. A store derivation has the fields the build
algorithm needs (thesis §2.4, Fig. 2.13; §5.4, Fig. 5.5):

| Field        | Meaning                                              |
| ------------ | ---------------------------------------------------- |
| `output`     | the store path the build must produce                |
| `inputDrvs`  | store paths of derivations that must be built first  |
| `inputSrcs`  | store paths of plain sources and build scripts       |
| `system`     | platform string, e.g. `i686-linux`; part of the hash |
| `builder`    | executable to run                                    |
| `args`       | command-line arguments                               |
| `envVars`    | the _complete_ environment, including `out`          |
| `outputHash` | non-empty only for fixed-output derivations          |

The two-stage split is the thesis's answer to language evolution and
distribution: a `.drv` is a stable, hashable, architecture-specific build
action, while the expression language can change above it (§2.4, pp. 39–41).
It also lets a client install a `.drv` directly, without evaluating the
expression that produced it.

### Realising a derivation

`nix-store --realise <drv>` runs the algorithm of §5.5.1 (Fig. 5.11), shown
there in its simple recursive form; the implementation actually uses the
parallel goal-state-machine of §5.5.4. In outline:

1. If the derivation itself is absent, try a substitute for it; abort if that
   fails.
2. If the output path is already valid, or a substitute can make it valid,
   stop — this is the cache hit.
3. Recursively realise every `inputDrvs` entry, and take the closure of their
   outputs plus `inputSrcs`.
4. Acquire an exclusive lock on the output path; re-check validity (another
   process may have finished first).
5. Refuse if `system` is not this machine, unless a build hook handles it.
6. Delete any residual output, create a fresh temporary directory, and run the
   builder with exactly `envVars` — no inherited `PATH`, with `HOME` set to
   `/homeless-shelter` and `PATH` to `/path-not-set`.
7. Canonicalise the output; for a fixed-output derivation, verify the declared
   hash.
8. In one database transaction, mark the path valid, record its content hash,
   scan for references, and record the deriver.

The algorithm is deliberately small. Distribution, substitutes, garbage
collection and user environments are layered on the same store tables and the
same validity/closure invariants.

### Derivations in à la carte terms

[concepts] fixes the comparison vocabulary, so this page only classifies Nix
against it. The à la carte paper places Nix in the **suspending scheduler ×
deep constructive traces** cell (JFP 2020 Table 2, Fig. 11) and calls its task
description **monadic**: a dependency can be computed from a value, and a
Nix expression can `import` the output of a derivation, so the graph is not
recoverable by inspecting the description alone.

| à la carte element | Nix realisation                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| key                | a store path (the output path; `nix-store --realise` also accepts the `.drv` path as a target)                                                          |
| value              | the immutable file-system object at that path                                                                                                           |
| task               | a store derivation: builder + args + complete environment + declared inputs                                                                             |
| persistent `i`     | the store database (`valid`, `references`, `referers`, `deriver`) plus the `.drv` files                                                                 |
| scheduler          | suspending, per the paper's model; realisation walks an already-instantiated `.drv` graph (simple recursion in §5.5.1, parallel goal machine in §5.5.4) |
| rebuilder          | deep constructive traces: the output path is keyed by a recursive hash of terminal inputs                                                               |
| early cutoff       | **no** — a dependency rebuilt from changed inputs gets a new path even if its bytes are unchanged                                                       |

The last row is the price of the cell: deep constructive traces judge a target
from terminal inputs, not from intermediate results, so Nix cannot stop a
rebuild cascade when an intermediate output is byte-identical. The thesis sees
the same limitation from the other side: a change to a header file "forces us
to rebuild all source files that include it … even for source files that
include the header but are unaffected" (§11.1, p. 247), and proposes making the
preprocessor an explicit derivation so unchanged preprocessed output can be
reused. That is early cutoff by another name, and it remains future work in
the thesis.

One qualification matters for readers coming from the paper. The à la carte
model classifies the _task description_; the thesis's Figure 5.11 recurses over
an already-instantiated `inputDrvs` list. Those are two levels: Nix's expression
evaluation is lazy and demand-driven, while realisation of a `.drv` is a
post-order walk. The classification is still correct — the graph is monadic in
the language, and the rebuilder is deep constructive in the store — but a
"topological" reading of Figure 5.11 is not a contradiction.

### What Nix-the-build-system inherits, and what it adds

The thesis is primarily about deployment, but its Chapter 10 asks whether the
same machinery can replace a low-level build manager. It can, and the
inheritance is direct:

- **Inherited:** the derivation as the unit of work; the store path as the
  cache key; the closure as the deployment unit; substitutes as a binary cache;
  purity as the condition that makes the hash meaningful; garbage collection as
  the reclaimer.
- **Added by the thesis:** per-file build actions. `compileC` wraps a C compile
  in a derivation; `makeLibrary` links a set of objects; `dependencyClosure`
  grows a header-file set by running a scanner derivation and importing its
  output at instantiation time (§10.1, pp. 233–237). Because each step is a
  derivation, a change to a header, a flag, the compiler or the build script is
  a change to an input and therefore a rebuild.
- **Not solved:** recursive Nix. A builder that calls `nix-build` would create
  paths that are not declared inputs or outputs of the outer build; the thesis
  suggests a private store but does not implement it. The alternative — one
  gigantic build graph — is conceptually clean but would give even GNU Hello
  hundreds of thousands of nodes (§10.2, pp. 239–240).

> "However, there is an unresolved problem with Nix as a build manager: how can
> we use it recursively, that is, from within a Nix builder?"
>
> — Thesis §10.2, p. 239

NixOS adds the system layer: a module system that merges option definitions,
lazy evaluation of the resulting configuration, and an activation script for
the genuinely imperative residue (restarting services, managing `/var`
state, installing setuid wrappers). It does not add a new scheduler or
rebuilder. The build engine described in 2006 is the one the distribution
uses.

## The fixed analysis spine

### 1. Task model and scheduling

A task is a _derivation_: a builder, arguments, a complete environment and a
set of input derivations and sources, identified by the hash of that
description. The graph is explicit at the `.drv` level and monadic at the
expression level. The thesis gives a simple depth-first post-order algorithm
(§5.5.1) and then the parallel goal-state-machine that the implementation
actually uses (§5.5.4); independent derivations can be realised in parallel
because the store's fine-grained path locks and transactional registration make
concurrent builds safe (§5.5.1, pp. 110–111; §5.5.4). There is no restart or
speculation: a missing dependency is simply built before its dependent, because
the dependency list is already known. That is why the implementation looks
topological even though the paper's model is suspending.

### 2. Rebuilding and correctness

Nix's dirty check is not an mtime comparison. A key is current when its output
path exists and is registered valid; the path itself encodes the recursive hash
of the derivation's inputs. Recording a successful build is a transaction, so
an interrupted build leaves no valid path and can be retried without recovery.
Correctness rests on two invariants: _validity_ (a valid path exists) and
_closure_ (every reference of a valid path is valid), plus the assumption that
builders are deterministic. The NixOS article is explicit that this last
assumption is not enforced by the operating system; it measures how often it is
violated in practice (below). The alternative _intensional_ model goes further:
it makes the store content-addressable by building at a temporary path, hashing
the result, and rewriting hash parts in the output before renaming it
(§6.3.2). That removes the need to trust that a given path's contents match the
derivation when sharing: an impure build simply lands at a different content
address. The thesis reports only a prototype, however — "the prototype is not
usable yet" (§11.1, p. 247).

### 3. Dependency discovery

Build-time dependencies are _declared_, not traced. The store supplies the
enforcement: because no store path is in a default search path, a forgotten
dependency makes the compiler or linker fail rather than silently find a
system copy (§2.1, p. 22). Runtime dependencies are _discovered by scanning_
for hash parts in the output, which is format-independent but conservative:
a false positive adds a harmless edge, while a reference encoded in an
unexpected way (UTF-16, compressed data) can be missed. The thesis compares the
scan to conservative garbage collection and validates it empirically in
Nixpkgs (§7.1.5). This is the opposite trade from Rattle's syscall tracing
([perfect-dependencies]) and from PIE's recorded dynamic calls ([pie]):
Nix makes declaration cheap enough to be complete instead of inferring the
declaration from execution.

### 4. Store and caching

The thesis distinguishes two store models. The _extensional_ model — the one
implemented and the one the NixOS article describes — is input-addressed: an
output path is computed from the derivation before the build, so equal inputs
give equal paths but a rebuild from changed inputs gives a new path even when
the bytes are identical. The _intensional_ model is content-addressed: the path
is computed from the output's hash, with hash rewriting to handle
self-references, and it supports mutually untrusted users sharing one store.
The thesis treats the latter as the more powerful but unfinished model.

Caching has two layers. Locally, validity is the cache hit; remotely, a
_substitute_ is a prebuilt output fetched from a server. `nix-push` uploads a
closure as NAR archives; `nix-pull` registers a manifest, and `nix-store
--realise` downloads a substitute instead of building. The model is
"transparent source/binary deployment": binary deployment is an optimisation
of source deployment, and it degrades back to source when local modifications
change the store paths (§2.6, pp. 44–46). Garbage collection uses profiles and
generations as roots; `nix-store --optimise` hard-links identical files. None
of this is an action cache in the REAPI sense — there is no remote execution
protocol here, only remote build hooks and binary substitution.

### 5. Hermeticity and provenance

Hermeticity is approximated, not enforced by a sandbox in the thesis. The
builder gets a cleared environment, a fresh temporary directory, an
unprivileged UID and a patched dynamic linker that does not search default
directories; a chroot build is optional (§5.5.1, pp. 111–112; JFP §6.2). The
NixOS article turns this into a measurement. Two builds of 485 non-`fetchurl` derivations
produced 165,927 files and directories; one file name differed, and 5,059 files
(3.4%) differed in content, almost all from timestamps. After filtering known
timestamp-bearing formats, 644 files (0.4%) remained, and only 42 (0.03%) had a
different size; none caused an observable behaviour difference (JFP §6.2,
p. 30). The authors also report that in seven years they had not seen an
undeclared build-time dependency on another store path, or an undetected
runtime dependency on one.

Provenance is _traceability_, not attestation: the `deriver` table records
which derivation produced an output, and the `.drv` graph is the explanation of
the build. The model has no signatures, no SLSA/in-toto statements, and no
transparency log. Trust in a substituter is global in the extensional model;
the intensional model is the thesis's answer to that, because path equality
then implies content equality even across users with different trust relations
(§6.3, pp. 140–143).

### 6. Distribution

Distribution is the _build hook_ mechanism (§5.5.2, pp. 115–117): when a
derivation's `system` does not match the local machine, or when a hook chooses
to offload, Nix writes the input closure, output path and references into a
temporary directory and invokes `NIX_BUILD_HOOK`. A typical hook copies inputs
to the remote store, runs `nix-store --realise` there, and copies the output
back. Both stores must be at the same filesystem location, because store paths
are embedded in outputs. The hook is policy-free: scheduling, load limits,
authentication and machine selection belong to the hook. This is remote
execution in the deployment sense, not a content-addressed action cache; the
unit shipped is a closure of store paths, and the remote side is trusted to run
the same derivation.

### 7. Sparkles relevance

`build_primitives.task` already has the skeleton of a task graph: `TaskId` is a
stable semantic identity, `TaskGraph` carries edges and readiness, and
`TaskExecutor` schedules ready tasks and reports outcomes. What Nix contributes
is the missing _identity and store_ layer, not another scheduler:

- **Borrow the derivation key.** A task's cache key should be a hash of its
  action and the _transitive_ identities of its inputs, not a timestamp. That
  is what makes a result reusable across machines and what makes an undeclared
  input a build error instead of a stale success.
- **Borrow the closure invariant.** If Sparkles ever materialises outputs,
  "valid implies every reference is valid" is a cheap, checkable deployment
  contract; the current executor's `Succeeded`/`Failed`/`Blocked` outcomes do
  not express it.
- **Borrow the substitute check, not the global store.** A remote cache lookup
  before execution is the high-value part. A global `/nix/store` and a
  daemon are not required to get it.
- **Avoid deep constructive traces if early cutoff matters.** Nix's no-early-
  cutoff behaviour is exactly what a task-DAG engine should measure before
  copying: a header-only change rebuilds every dependent even when the object
  file is unchanged. The thesis's own future work (§11.1) is the fix.
- **Do not copy hash scanning blindly.** It works because store paths are
  distinctive and builders are isolated. A general task runner with ambient
  paths needs traced or declared discovery first ([perfect-dependencies],
  [pie]) and scanning only as a runtime-reference check.

## Strengths and weaknesses

- **Correct by construction, at the right level.** Complete dependencies,
  immutable outputs, atomic profile switches, O(1) rollback and safe garbage
  collection all follow from one representation. The thesis is unusually clear
  that these are consequences of the model, not features bolted on.
- **A small, durable kernel.** The `.drv` format, the validity/closure
  invariants and the realisation algorithm survived from 2006 into NixOS; the
  expression language and the packaging conventions changed around them.
- **Empirically large.** NixOS is not a toy: 2,481 packages in Nixpkgs as of
  May 2010, a 1,036-derivation system graph (582 excluding `fetchurl`), a
  487-path / 1,991 MiB runtime closure, and 560 Nix expression files evaluated
  in 1.5 s of CPU time (JFP §6.1, p. 27). The purity measurement is a real
  experiment, not an assertion.
- **No early cutoff.** Deep constructive traces rebuild dependents when an
  input derivation's identity changes, even if the new output is byte-identical.
  The cost is worst at the bottom of the graph: a Glibc change rebuilds the
  system.
- **Disk and rebuild amplification.** NixOS may need roughly twice the disk
  space during an upgrade (about 4 GiB versus 2 GiB for the measured
  configuration); `nix-store --optimise` recovered 1,139 MiB (57.3%) by
  hard-linking 77,702 of 89,150 files in one rebuild (JFP §6.2, pp. 30–31).
- **Purity is assumed, not enforced.** The 2006/2010 system clears the
  environment and uses an unprivileged UID, but does not sandbox syscalls or
  network access by default; the measured impurity rates are small but nonzero,
  and the authors are explicit that a hostile builder can defeat the model.
- **Declaration is still work.** Nix makes a missing declaration fail, but the
  packager must still write it; `dependencyClosure` helps for C headers and
  does not generalise to every language. The coarse package granularity is a
  deliberate trade, not an oversight.
- **Trust, not provenance.** A binary substitute is trusted as the output of
  its derivation; the extensional model has no per-substituter trust boundary.
  The intensional model addresses this but remained a prototype in the thesis.

## Key design decisions and trade-offs

| Decision                                           | Rationale                                                                                                          | Trade-off                                                                                                                    |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Immutable store paths keyed by all inputs          | Non-interference, side-by-side versions, atomic upgrade/rollback, and a cache key that is also a provenance record | Every input change creates a new path: rebuild cascades, disk growth, and no early cutoff                                    |
| Two-stage expression → `.drv` → build              | A small stable IR survives language evolution; derivations can be shipped and realised without the expression      | An extra indirection and a graph that can become very large; the thesis leaves recursive Nix unresolved (§10.2)              |
| Declared inputs enforced by store isolation        | Complete build dependencies without syscall tracing; a forgotten dependency fails instead of silently succeeding   | Runtime dependencies still need discovery; ambient non-store paths remain an impurity source                                 |
| Hash scanning for retained runtime dependencies    | Format-independent, cheap, and good enough for conservative closure computation                                    | False positives add edges; non-standard encodings can be missed; it is not a substitute for tracing in a non-isolated system |
| Deep constructive traces (input-addressed outputs) | One lookup on terminal inputs; shallow deployment works without materialising intermediates                        | Determinism is required; no early cutoff; equal bytes from different inputs are stored twice                                 |
| Extensional model first, intensional model later   | Input addressing is simple, fast and already gives complete deployment and binary substitution                     | Content-addressed sharing and per-user trust need hash rewriting and a store design the thesis only prototypes               |
| Binary substitutes as an optimisation              | Source deployment stays the semantic model; users get binary speed without a second package format                 | The substituter is trusted globally in the extensional model; no signature or attestation layer                              |
| NixOS modules + activation script                  | Declarative composition of the static system, with a narrow imperative boundary for running services               | Mutable state, database migrations and setuid wrappers stay outside the model; activation is not rollback-safe for state     |
