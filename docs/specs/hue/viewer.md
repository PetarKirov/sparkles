# `hue` viewer — Feature Requirements (scoped by interaction tier)

_**Status:** living inventory · **Date:** 2026-08-29 · **Scope:** every viewer
requirement that is **not** specific to one backend. What a GPU window owns is in
[gui.md](./gui.md); what a terminal owns is in [tui.md](./tui.md); everything
else is here, scoped by the interaction tier it needs rather than by the canvas
that happens to paint it._

## Why this file exists

Requirements used to be filed **by backend**, and that produced defects rather
than merely reading oddly. hue's in-document search was specified once in
`gui.md` and nowhere in `tui.md`, and the two implementations silently diverged
on four axes — case sensitivity, haystack, granularity and jump placement. A
backend-shaped spec cannot express "these must agree", because it has no place to
say it.

> [!IMPORTANT]
> **A divergence between the GUI and the TUI is a defect, not a variation.**
> Where a tier is achievable in a backend, the behaviour must be identical; where
> it is not, the row states the degradation explicitly. See
> [`UIA13`](./ui-architecture.md).

## Tiers

From `sparkles.input.tier.InteractionTier`:

| Tier                    | Meaning                                                                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `passive`               | Expressible in static output — no event loop needed                                                                                   |
| `interactive`           | Needs a live event loop (key, pointer, wheel traffic)                                                                                 |
| `precise`               | Needs sub-cell positions or continuous time                                                                                           |
| `precise → interactive` | Precise where the canvas allows it, degrading to cell/step granularity where it does not — the degradation is part of the requirement |
| `invariant`             | Not an interaction requirement at all: an architectural or performance rule that holds at every tier                                  |

> [!WARNING]
> **No row in this file may assume a frame clock.** `WIN1` gives the window a
> 60 fps loop; `TSF1` gives the terminal one frame per repaint; `TKB4` states
> flatly that "a terminal has no frames". Any requirement expressed in elapsed
> time must therefore name a duration and let each host reach it its own way —
> never a frame count.
